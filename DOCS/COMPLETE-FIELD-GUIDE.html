Chapter 02

Stages 0–3: Spine, Dashboard, Persistence, Docker

Stage 0 — the spine. main.py receives an OpenAI-style request, routes it to a provider, times it, records telemetry, returns the answer. This established the two things everything needs: one point every request flows through, and one place every request is recorded.

Stage 1 — the dashboard. dashboard.html is a pure reader of your /telemetry endpoints — no database of its own. The summary cards are the metrics pillar; the request table is the logs pillar.

Stage 2 — persistence. You swapped the in-memory list for SQLite behind the same TelemetryStore interface, so nothing else changed. That "stable interface hiding the implementation" idea is the backbone of the whole codebase — and it's exactly what makes Stage 7's Postgres swap possible.

Stage 3 — Docker. Your Dockerfile + docker-compose.yml package the app (and Redis) so docker compose up --build runs everything identically anywhere. This is the unit Kubernetes will later orchestrate.

The Thread ▸

Notice the pattern already forming: each layer hides its details behind a clean boundary. Storage hides behind TelemetryStore. The app hides behind a container. This is the single idea that scales all the way up to Stage 7.

Chapter 03

Stage 4: Routing & Failover

routing.py is pure logic — no network, no database. It returns an ordered list of (provider, model) attempts: routing (cheap tier for simple prompts, strong tier for complex) plus failover backups. main.py walks that list, trying each until one succeeds, recording every attempt as telemetry.

The key behavior to defend: a long prompt with no provider and no API key does not error out. The router picks the strong tier (anthropic); it fails with no key; that failure is recorded; the loop continues to the next attempt (mock), which succeeds. The request survives — that is the entire point of failover. You also upgraded this later to tell a client error (don't fail over) apart from a provider error (do) — a genuinely sharp addition.

Why routing.py Is Pure ▸

Decisions live apart from side-effects. Routing decides; main.py acts. That makes routing testable with no mocks or keys, and lets you change strategy without touching how requests are recorded. Same reason TelemetryStore hides storage — the one design idea, applied again.

Chapter 04

Stage 5: Alerting

alerts.py is another pure module: it takes recent telemetry in and returns fired alerts out. Four rules — error-rate spike, provider-failure burst, cost spike, latency spike — each with tunable thresholds at the top. main.py's /alerts endpoint reads recent telemetry, runs the rules, logs anything that fires.

The mindset shift this stage taught: alerting only makes sense from the operator's chair. A user never wants an alert; the company running the system needs to know a provider is degrading before it becomes a visible outage. And it stays strictly on operational signals (cost, latency, errors) — never the unsolved "was the answer good" problem.

Your Thresholds ▸

You own the numbers. The honest interview answer to "how did you set them?" is: "started conservative, made them tunable constants, would refine against real traffic." That you put them at the top of the module (and in values.yaml) proves you designed for tuning.

Chapter 05

Stage 6: Guardrails & OpenTelemetry

Guardrails (guardrails.py) are the safety checkpoint — the "is this allowed?" layer, distinct from "is this good?". Input/output checks for things like prompt injection and PII, recorded when they trigger. This shows a control plane isn't only about performance and cost; it's also where safety policy is enforced.

OpenTelemetry (otel.py) is the piece you said is still fuzzy, so here it is plainly: OTel is a vendor-neutral standard for emitting telemetry, so any monitoring tool can read your data without custom glue — the "USB port" of observability. Your file emits two signal types: traces (spans — a timed, labeled unit of work; trace_span wraps each request) and metrics (a request counter, a latency histogram, a cost counter, all with provider/model/status labels).

The Honest Nuance ▸ (worth knowing before an interview)

Your telemetry.py → your dashboard is a loop you built for yourself. OTel emits the same signals in the standard format so external, industrial tools (Grafana, Jaeger, Prometheus) can consume them with zero custom work. In your current code, traces print via a console exporter, and the metric instruments are recorded but not yet wired to an exporter/reader — so the visible metric output is the manual print. Totally fine for learning; just say exactly that ("traces export to console; wiring metrics to Prometheus is adding an OTLP exporter") rather than claiming full Grafana integration.

Chapter 06

The Big Idea: Statelessness

Everything in Stage 7 exists to serve one idea, so start here. Your app stored telemetry in a local SQLite file. That's fine for one copy. But to handle real traffic you run many copies (replicas) of the service — and if each copy has its own local file, no copy sees the full picture. The data is fragmented.

The fix is statelessness: the service itself holds no local state; all shared state moves to shared backends. That's exactly what you built — a pluggable TelemetryStore where an environment variable (TELEMETRY_BACKEND) selects SQLite (local, single node) or PostgreSQL (a shared network database all replicas talk to). Your test_statelessness.py proves it: multiple replicas, one shared Postgres, and /telemetry returns a consistent full picture no matter which replica served each request.

Stateful replicas are like cashiers who each keep their own private notebook of sales — ask any one and you get a partial answer. Stateless replicas are cashiers who all write to one shared ledger — ask any of them and you get the whole truth. Postgres is the shared ledger.
Why This Is THE Stage-7 Answer ▸

If an interviewer asks one question about your deployment, it's "how does this scale?" The answer is this chapter: "the service is stateless — telemetry in shared Postgres, counters in shared Redis — so I run N replicas behind a load balancer and they behave as one." That sentence is your distributed-systems background showing, and you built the proof.

Chapter 07

Docker → Kubernetes → Helm → Terraform (the ladder)

These four tools confuse people because they sound similar but sit at different rungs of one ladder. Here's the whole thing in order, each building on the last:

RungAnswers the questionIn your project
Docker"How do I package one app to run anywhere?"Your Dockerfile — one container image of the control plane.
Kubernetes"How do I run many copies of that container, keep them alive, and network them?"Your k8s/ manifests — Deployment (replicas), Service (networking), ConfigMap/Secret (config), plus Postgres & Redis.
Helm"How do I package all those Kubernetes files into one installable, configurable unit?"Your chart/ — templated manifests + values.yaml. One helm install deploys everything.
Terraform"How do I create the cluster and everything around it as code, from nothing?"Your terraform/ — provisions the environment and deploys your Helm chart.

Read that top to bottom and the confusion dissolves: Docker packages one app; Kubernetes runs many; Helm packages the Kubernetes setup; Terraform provisions the whole environment. Each rung wraps the one below it.

Key Distinction ▸ Helm vs Terraform

The one people mix up. Helm deploys applications onto a Kubernetes cluster. Terraform provisions infrastructure — including the cluster itself, plus databases, networks, and, yes, it can then invoke Helm. Rule of thumb: Terraform builds the house (and the plot of land); Helm moves your furniture in. Your Terraform literally does both — it makes the namespace and then calls your Helm chart.

Chapter 08

What Terraform Is Actually Doing (in YOUR files)

You said Terraform is the fuzzy one — "something deployed in production on GCP/AWS that I don't know yet." Let's fix that using your terraform/main.tf, because you've actually already used it; you just haven't named what it did.

What Terraform is, in one line: a tool that lets you describe infrastructure in text files and create it with one command (terraform apply) — so your infrastructure is version-controlled, reviewable, and reproducible instead of clicked together by hand. That's Infrastructure as Code.

Your file has three parts. First, it declares which providers (plugins) it needs — the kubernetes and helm providers:

terraform {
  required_providers {
    kubernetes = { source = "hashicorp/kubernetes" }
    helm       = { source = "hashicorp/helm" }
  }
}

Second, it creates a resource — a Kubernetes namespace to deploy into:

resource "kubernetes_namespace" "llmops" {
  metadata { name = var.namespace }
}

Third — and this is the important part — it uses a helm_release resource to deploy your Helm chart, passing in values like replica count and the API key:

resource "helm_release" "llmops" {
  name      = "llmops"
  chart     = "../chart"
  namespace = kubernetes_namespace.llmops.metadata[0].name
  values    = [ /* replicaCount, secrets... */ ]
}

So what your Terraform actually does: with one terraform apply, it creates a namespace and installs your entire Helm chart (app + Postgres + Redis) into your cluster. It's the single "on switch" for the whole platform. That's not a mystery anymore — that's the file you already wrote.

The Mental Model ▸ Declarative

Terraform is declarative: you describe the end state you want ("a namespace, and my chart installed"), and Terraform figures out how to get there — creating what's missing, and (if you change the file and re-apply) updating only what changed. You don't write step-by-step commands; you declare the destination. Same philosophy as your Kubernetes YAML, which declares "I want 2 replicas" rather than "start a replica, then start another."

Try This ▸

Open terraform/main.tf and read the big comment block at the top — you (or your AI) wrote a clear "cloud swap note" there. Trace how the helm_release resource stays identical whether you target local or cloud. When you can explain those three parts (providers, namespace resource, helm_release) out loud, Terraform is no longer fuzzy — you understand your own file.

Chapter 09

How the Cloud Swap Works (GCP/AWS)

Your instinct — "Terraform is really used in production on GCP/AWS" — is exactly right, and your project is set up to show precisely that transition. You deployed to local Kubernetes (kind/minikube) on purpose: it teaches the identical skills without a cloud bill. The leap to production is smaller than it looks, and your files even document it.

Two things change when you go to real cloud, and nothing else does:

  • The cluster. Instead of a local cluster, Terraform provisions a managed one — EKS on AWS or GKE on GCP — usually via a ready-made module (your comment block literally shows module "eks").
  • The stateful backends. Instead of running Postgres and Redis as pods in the cluster, you point at managed services — AWS RDS (Postgres) and ElastiCache (Redis) — because a real company wants the cloud provider to run their database, not a pod.

The crucial insight, and a great thing to say in an interview: your helm_release stays 100% identical. The application, the chart, the Kubernetes manifests — all unchanged. Only the infrastructure underneath (the cluster and the databases) swaps from local to managed cloud. That's the whole payoff of building it this way: the same artifact deploys anywhere.

Why You Don't Need To Do It Now ▸

Provisioning real EKS/GKE costs money and hours and teaches nothing beyond what your local setup already taught. For your goal, "it deploys to any Kubernetes cluster — here's the Helm chart and Terraform, and here's exactly where the cloud swap happens" is a complete, strong answer. You've demonstrated the skill. Spend the cloud bill later, when a job is paying for it.

Chapter 10

How to Actually Master These

You said the real problem: "I know what the terms do, but other than that I'm not aware — how do I master the concepts?" Here's the honest truth about mastering infrastructure tools, because it's different from mastering, say, an algorithm.

You don't master them by reading. You master them by breaking and fixing them. Infra knowledge is almost entirely troubleshooting knowledge — nobody memorizes Kubernetes; they've just debugged enough broken pods to have intuition. The path is deliberately hitting failures and recovering. Concretely, on your own project:

The Mastery Drills ▸ (do these on your finished project)
  • Break a pod. Set the image tag to something wrong and helm upgrade. Watch it fail (kubectl get pods → CrashLoopBackOff), then kubectl describe pod and kubectl logs to diagnose it, then fix it. This one drill teaches more than a week of reading.
  • Scale it live. Change replicaCount from 2 to 5, re-apply, and watch kubectl get pods show five. Then kill one (kubectl delete pod ...) and watch Kubernetes recreate it. That's what "self-healing orchestration" means — you'll never forget it after seeing it.
  • Prove statelessness yourself. Run your test_statelessness.py, then read it and explain why hitting different replicas still returns one consistent telemetry picture (shared Postgres).
  • Change one Terraform value and re-apply. Bump replica_count in terraform.tfvars, run terraform plan (read what it says will change — this is the magic: it shows you the diff before doing it), then terraform apply. Watching plan predict the change is the moment Terraform clicks.
  • Follow one request end-to-end with kubectl. kubectl port-forward to your service, hit /dashboard, send a request, watch it appear. Connecting "my laptop command" to "running in a cluster" is the intuition that matters.

Do those five, and you'll have operated the tools, not just read about them — which is the only kind of mastery that survives an interview or a 3am incident. The commands above (kubectl get/describe/logs, helm upgrade, terraform plan/apply) are 90% of what you'll ever use day to day.

The Realistic Bar ▸

You do not need to be a Kubernetes expert to get hired for AI-infra roles — you need to have genuinely deployed a real service and be able to reason about it. You've done that. "Mastery" here means comfortable troubleshooting and clear mental models, not memorizing every API object. Aim for that bar; you're close to it.

Chapter 13

Glossary of Stage-7 Terms

Container (Docker)
A portable package of an app + its dependencies that runs identically anywhere. Your Dockerfile builds one.
Image / Registry
A built container is an "image"; a "registry" is where images are stored/shared (e.g. Docker Hub).
Kubernetes (K8s)
The orchestrator that runs many containers across machines — restarting, scaling, networking them.
Pod
The smallest deployable unit in Kubernetes — usually one container. Your app runs in pods.
Deployment
A Kubernetes object that keeps a desired number of identical pods running (your replicaCount).
ReplicaSet
The set of identical pods a Deployment manages.
Service
A stable network endpoint in front of a set of pods (pods have no stable IP; the Service does).
ConfigMap
Kubernetes object holding non-secret config (your alert thresholds, backend choice).
Secret
Kubernetes object holding sensitive values (your ANTHROPIC_API_KEY, DB URL). Never committed.
Namespace
A logical partition inside a cluster (your Terraform creates the llmops namespace).
Ingress
Routes external traffic into cluster Services (or use port-forward locally).
Volume
Storage that outlives a pod — needed for stateful things like a database.
Helm
A package manager for Kubernetes; a "chart" bundles templated manifests + values.yaml.
Chart / values.yaml
Your chart/ is the package; values.yaml holds the knobs an operator tunes.
Terraform
Infrastructure-as-code: describe infrastructure in files, create it with terraform apply.
Provider (Terraform)
A plugin that lets Terraform manage a system (you use the kubernetes and helm providers).
Resource (Terraform)
One thing Terraform manages (your namespace, your helm_release).
helm_release
A Terraform resource that installs a Helm chart — how your Terraform deploys your app.
terraform plan / apply
plan shows what will change before doing it; apply makes it happen.
Declarative
You describe the desired end state; the tool figures out how to reach it. K8s and Terraform both work this way.
Stateless
The service keeps no local state; shared state lives in shared backends — the key to horizontal scaling.
Horizontal scaling
Handling more load by running more copies (replicas), not a bigger single machine.
EKS / GKE / AKS
Managed Kubernetes on AWS / GCP / Azure — the cloud swap for your local cluster.
RDS / ElastiCache
AWS managed Postgres / managed Redis — the cloud swap for your in-cluster Postgres/Redis.
