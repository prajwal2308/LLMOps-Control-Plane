Part I

The Blueprint

The whole project in three chapters: what it is, how the pieces fit, and why each tool was chosen. Read this part once, fully, before touching a stage.

Chapter 01

What You're Building (one page)

A self-hostable LLMOps control plane: a service that sits between applications and the LLM providers they use, and gives a team visibility and control over every model call — latency, tokens, cost, errors, which provider served it — plus the operational muscle to route, protect, and alert on that traffic.

The problem it solves. Most companies don't train models; they call OpenAI, Anthropic, or a local model. That leaves them with no single place to answer basic operational questions: What is this costing us? Which requests are slow? What happens when the provider goes down? Is any of this leaking sensitive data? Your control plane is that single place.

The One-Sentence Pitch ▸

"A self-hostable control plane that sits in front of LLM applications and gives you per-request observability — latency, token, and cost telemetry — plus routing, failover, alerting, and guardrails, deployed as infrastructure-as-code." Memorize this. It's your answer to "what is this?"

Why it's the right project for you. Its delivery layer — containers, Kubernetes, Terraform — is your existing strength. Only the AI-specific middle (telemetry for LLM traffic) is new, and you now understand it. And it lives entirely in the durable part of the field: observability, metrics, caching, and reliability don't churn with each new model — they only deepen. You are building on bedrock.

Cross-Reference ▸

Every concept in this handbook was defined in the Field Guide. Where you see "(FG Ch. 12)" it points back to the relevant chapter there. Keep both open.

Chapter 02

The Architecture, End to End

The mental model is a pipeline: a request enters, passes through a series of stages, reaches a provider, and the response comes back — with the control plane observing and shaping it the whole way. Here is the full journey a single request takes once the project is complete:

  App
   │  (1) sends an OpenAI-style request
   ▼
┌─────────────────────  CONTROL PLANE  ─────────────────────┐
│  (2) authenticate / identify the caller                   │
│  (3) check rate limit + budget          → Redis           │
│  (4) input guardrails (injection, PII)                    │
│  (5) check cache (exact, then semantic) → vector store    │
│  (6) ROUTE to a provider                                  │
│         ├─ primary  → OpenAI / Anthropic / local          │
│         └─ on failure → FAILOVER to backup                │
│  (7) output guardrails                                    │
│  (8) RECORD telemetry (latency,tokens,cost) → store       │
│  (9) evaluate alert rules (spike? error burst?)           │
└───────────────────────────┬───────────────────────────────┘
   │  (10) return response + usage
   ▼
  App        …and a Dashboard reads the telemetry store live.

Not every stage exists yet — most are the stages you'll build in Part II. But hold this whole picture in your head from day one, because each stage you add is one box in this diagram becoming real. The spine you already built is boxes (1), (6-primary), (8), and (10).

Key Idea ▸ The Control Plane vs the Data

The term "control plane" is borrowed from networking. The control plane is the layer that makes decisions and observes (route this, block that, record this); the actual model responses flowing through are the "data plane." Naming your project a control plane is accurate and signals systems literacy — you're managing traffic, not hosting models.

Try This ▸

Draw this diagram by hand, from memory, and circle the four boxes you've already built. Do it again after each stage, circling the new box. By Stage 7 you'll be able to reproduce the entire architecture on a whiteboard — which is exactly what a systems-design interview asks for.

Mental Model ▸ REST APIs, Web Frameworks & Architecture

1. REST API vs. FastAPI (Abstraction Layer): A REST API is an architectural pattern for web communication over HTTP (using methods like GET and POST to exchange JSON). FastAPI is the Python web framework that acts as an abstraction layer — "covering up" raw network socket listening, HTTP header parsing, and serialization so you only write clean Python functions. Other languages use similar framework abstractions: JavaScript/Node.js (Express.js, Fastify), Java (Spring Boot), and Go (Gin).

2. Frontend vs. Backend Split: React runs strictly in the browser (Frontend UI) and cannot safely store secret API keys (like ANTHROPIC_API_KEY) or query databases directly. Backend frameworks (FastAPI, Express) run on private servers to manage keys, database queries, and business logic. Next.js is a full-stack framework that combines React UI on the frontend with a built-in Node.js server (API routes) on the backend. We use Python + FastAPI for this control plane because Python is the native ecosystem of AI/ML infrastructure.

Scope Discipline ▸

This is a lot of tools eventually. The trap that kills portfolio projects is trying to add them all at once. You will add exactly one per stage, get it working and understood, then move on. A finished 4-stage project beats an abandoned 8-stage one every single time.

Chapter 04
Stage 0 · Done

The Spine You Already Have

What it is. A FastAPI service with an OpenAI-compatible endpoint that routes a request to a provider (a keyless mock, or real Anthropic), times it, records telemetry (latency, tokens, cost, status), and exposes that telemetry. Three clean modules: providers.py, telemetry.py, main.py.

Why it's the foundation. It establishes the two things everything else needs: a single point every request flows through, and a place every request gets recorded. Boxes (1), (6), (8), (10) of the architecture diagram are already real.

Done When ▸ (already true)

python test_smoke.py runs requests end to end and prints a telemetry summary, including a deliberately-triggered error. The server runs with uvicorn app.main:app --reload and serves interactive docs at /docs.

Before Moving On ▸

Read main.py top to bottom until the request-flow comment (request → route → time → record → return) is obvious to you. This is the file every interview question about your project will circle back to. If it's clear, you're ready for Stage 1.

Chapter 05
Stage 1 · Next

The Live Dashboard

Goal. Turn invisible telemetry into a page you can see — the single most motivating stage, because it makes the project demoable and screenshot-worthy.

What you build. A single web page that calls your existing /telemetry and /telemetry/summary endpoints and renders them: summary cards at the top (total requests, total cost, average latency, error count) and a live table of recent requests below, refreshing every couple of seconds.

The key idea. The backend already returns JSON. The dashboard is just a reader of that JSON — no new backend logic. In its simplest form it's one HTML file with a little JavaScript:

// the entire heart of the dashboard
async function refresh() {
  const summary = await (await fetch('/telemetry/summary')).json();
  const rows    = await (await fetch('/telemetry')).json();
  renderCards(summary);   // draw the 4 top numbers
  renderTable(rows);      // draw the request log
}
setInterval(refresh, 2000);   // update every 2 seconds

We serve that file from FastAPI so it lives at, say, /dashboard. That's it — a live operations view of your control plane.

Concepts Used ▸

The metrics and logs pillars of observability (FG Ch. 12): the summary cards are metrics, the table is logs. You're building the "dashboard" half of "telemetry + dashboard = observability."

Done When ▸

You open /dashboard, fire a few requests (via /docs or curl), and watch the numbers and the table update on their own. That live update is your demo.

Honest Note ▸

Keep it plain HTML/JS for now. It's tempting to reach for React and a component library, but that's a detour that adds hours and hides the point. A clean, simple page that clearly shows live telemetry is more impressive than a half-built fancy one. Style can come last.

Chapter 06
Stage 2

Persistent Storage

Goal. Make telemetry survive a restart. Right now it lives in an in-memory list that vanishes when the server stops — fine for a demo, wrong for anything real.

What you build. Swap the in-memory list inside TelemetryStore for SQLite — a real database that's just a single file, needs zero setup, and ships with Python. The beauty of how Stage 0 was built: only the inside of TelemetryStore changes. Its methods (record, all, summary) keep the same signatures, so main.py and the dashboard don't change at all.

Why This Design Matters ▸

This is your first taste of a real engineering principle: separation of concerns behind a stable interface. Because the store hides how it stores, you can change the storage engine without touching anything else. In an interview: "I put persistence behind the store's interface, so swapping in-memory for SQLite — and later Postgres — is a one-file change." That sentence signals real design maturity.

Concepts Used ▸

Data persistence; the idea that observability data is only useful if it outlives the process. Sets you up for querying history (last hour, error rate over time) which alerting (Stage 5) needs.

Done When ▸

You send requests, restart the server, reload the dashboard — and the past requests are still there. A .db file now holds your telemetry.

What's Next (later) ▸

When you deploy to Kubernetes (Stage 7), you'll graduate SQLite → PostgreSQL, because multiple copies of the service need a shared database. Same interface, bigger engine. Note it now; do it then.

Chapter 07
Stage 3

Containerize with Docker

Goal. Package the whole service into a container so it runs identically anywhere — your laptop, a server, the cloud. Small effort, big payoff, and it's a prerequisite for Kubernetes later.

What you build. A Dockerfile (the recipe) and a docker-compose.yml (to run your service alongside Redis in one command). The Dockerfile is short:

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

Then docker compose up builds and runs everything. Anyone in the world can now run your control plane with that one command, no Python setup required.

Concepts Used ▸

Containers and reproducibility (FG Ch. 17). This is squarely your existing strength — the AI-specific part is behind you; from here the project increasingly rewards what you already know.

Done When ▸

docker compose up starts your service (and Redis), and the dashboard works at localhost:8000/dashboard — all without you having Python or dependencies installed locally.

Try This ▸

After it works, add a one-line badge to your README: "Run it: docker compose up." Reviewers love a project that runs in one command — it signals you think about the person receiving your work, which is itself an engineering virtue.

Chapter 08
Stage 4

Routing & Failover

Goal. The reliability centerpiece. Make the control plane survive a provider outage and choose smartly between providers — the feature that most says "this person understands production."

What you build. Two related capabilities on top of your provider abstraction:

  • Failover: if the primary provider errors or times out, automatically retry the request on a backup provider — so the caller never sees the outage.
  • Routing: choose which provider/model handles a request based on a rule (e.g., cheap model for short/simple prompts, strong model for long/complex ones).

Because Stage 0 already abstracts providers behind a common generate() call, failover is a loop with a fallback:

def call_with_failover(order, model, messages):
    last_error = None
    for provider_name in order:            # e.g. ["anthropic", "openai", "mock"]
        try:
            return get_provider(provider_name).generate(model, messages)
        except Exception as e:
            last_error = e                 # record it, then try the next one
    raise RuntimeError(f"all providers failed: {last_error}")

Every attempt — including the failovers — gets recorded as telemetry, so the dashboard shows exactly when a failover happened. That visibility is the demo.

Concepts Used ▸

Routing, failover, and production reliability (FG Ch. 11, 16). This is the distributed-systems thinking that's core to your background — retries, fallbacks, graceful degradation.

Done When ▸

You configure a bad primary provider (or kill it mid-run) and watch requests seamlessly succeed via the backup, with the failover visible in the telemetry. Nothing dropped.

Honest Note ▸ Do It Well

Real failover has subtleties: retries with exponential backoff (wait a bit longer each retry), circuit breakers (stop hammering a provider that's clearly down), and timeouts. You don't need all of it on day one, but know the terms — an interviewer will ask "what about retry storms?" and "how do you avoid failing over on a user error vs a provider error?" Having thought about it is the point.

Interview Mastery ▸ Operational Trade-offs Answered

1. What about retry storms?

The Problem: If an upstream LLM provider (e.g. OpenAI or Anthropic) suffers a brief latency spike or transient failure, thousands of incoming client requests fail simultaneously. If every client retries immediately, the sudden 3x–5x spike in traffic acts as a self-inflicted Distributed Denial of Service (DDoS) attack on the provider, turning a minor glitch into a prolonged blackout.

Production Mitigation Strategy:

  • Exponential Backoff + Full Jitter: Calculate delay as T = random(0, min(max_backoff, base_delay * 2^attempt)). Adding randomized jitter desynchronizes retry bursts, spreading traffic smoothly across time.
  • Circuit Breaker Pattern: Monitor rolling error rates (e.g., 5 consecutive failures in 10s). When tripped, set state to OPEN and fail fast (or route directly to secondary fallback) for a cooldown period (e.g. 30s) without sending traffic to the unhealthy primary.
  • Global Retry Budget: Restrict retries so they consume at most 10% of total system throughput. If the budget is exhausted, return errors immediately instead of hammering down services.

2. How do you avoid failing over on a user error vs a provider error?

The Problem: Retrying or failing over on a client error (e.g., bad client key, malformed JSON, or prompt exceeding context window) is an antipattern. The secondary model will fail with the exact same error, wasting budget, inflating latency, and polluting fallback metrics.

Production Mitigation Strategy:

  • Strict Error Taxonomy (HTTP 4xx vs 5xx):
    • 4xx Client Errors (400, 401, 403, 422): Non-retryable. Fail fast immediately and return the 4xx error directly to the caller.
    • 5xx Provider Errors (500, 502, 503, 504, Connection Timeout, DNS failure): Retryable / Failover-eligible. Trigger the secondary attempt plan automatically.
  • Gateway Boundary Validation: Validate request schemas via Pydantic / JSON Schema before initiating the attempt loop so syntax or payload errors never reach the provider layer.

3. What happens step-by-step when a long prompt arrives with no provider specified and no API key set?

Step-by-Step Execution Lifecycle:

  1. Gateway Entry: FastAPI parses the request body. req.provider is None.
  2. Complexity Classification: estimate_complexity(messages) measures total prompt length (> 280 chars) and classifies it as "complex", routing it to STRONG_TIER (anthropic:claude-3-5-haiku-20241022) as Primary Attempt #1.
  3. Attempt Plan Assembly: Ordered plan becomes ["anthropic:claude-3-5-haiku-20241022", "mock:mock-model"].
  4. Primary Attempt Failure: Attempt #1 executes against Anthropic. Because ANTHROPIC_API_KEY is unconfigured on the server, it raises a ProviderError (5xx infrastructure fault). The gateway records an ERROR row in SQLite ([attempt 1/2] ANTHROPIC_API_KEY is not set).
  5. Resiliency Backoff & Failover: Controls plane calculates exponential backoff with full jitter (calculate_backoff_with_jitter(attempt=0)), sleeps for a randomized delay, and advances to Attempt #2 (mock:mock-model).
  6. Graceful Degradation: Attempt #2 (mock) succeeds, records an OK telemetry row, and returns HTTP 200 OK to the client with full routing audit metadata.

4. Isn't a missing API key a user authorization error (HTTP 401) instead of a provider outage?

System Infrastructure Keys vs. End-User Credentials (BYOK):

  • Backend Infrastructure Key (Current Gateway Architecture): The ANTHROPIC_API_KEY belongs to your platform's server environment. End-users do not provide Anthropic keys. If your server's key is missing or invalid, that is a backend service outage on your side (HTTP 5xx). The gateway automatically fails over to the backup model so your user experiences zero downtime.
  • Bring-Your-Own-Key Pattern (BYOK / User Credentials): If end-users pass their own personal API keys in request headers (e.g. x-api-key: user-key) and send an invalid key, that is a User Error (HTTP 401 Unauthorized). Under our ClientError taxonomy, the gateway fails fast immediately with failed_over: false and returns HTTP 401 without retrying or failing over.
Chapter 09
Stage 5

Alerting on Anomalies

Goal. Move from watching to being warned. A dashboard needs a human looking at it; alerting catches problems when no one is.

What you build. A small rule engine that runs after each request (or on a timer) and checks the recent telemetry for trouble:

  • Latency spike — recent average latency far above normal.
  • Cost spike — spend in the last window above a threshold.
  • Error burst — error rate over the last N requests above a limit.
  • Provider outage — a provider failing repeatedly.

When a rule fires, you emit an alert — to the dashboard (a banner), the logs, or a webhook (e.g., a Slack message). The rules read the persistent telemetry from Stage 2, which is why persistence came first.

Design Boundary ▸ Operational, Not Quality

Keep alerts on operational signals — latency, cost, errors, provider health — all of which are objectively measurable. Do not try to alert on "the answer was bad." Judging open-ended answer quality has no reliable automated solution (FG Ch. 15), and reaching for it would drag your finishable project into an unsolved research problem. Staying on measurable operational signals is what keeps this shippable — and knowing why you drew that line is exactly the judgment interviewers probe for.

Concepts Used ▸

Monitoring and the spirit of drift detection (FG Ch. 13) — catching when live behavior diverges from normal. This is MLOps thinking applied to LLM traffic.

Done When ▸

You trigger a cost or error spike (easy with the mock provider) and an alert fires — visible on the dashboard and/or sent to a webhook. The system now warns without a human watching.

Chapter 10
Stage 6 · High-Value

Guardrails & OpenTelemetry

Two additions that each raise the project's ceiling — one for safety, one for standards. Do them together as the "maturity" stage.

Guardrails

Goal. Add a safety checkpoint to the pipeline — the "is this allowed?" layer (FG Ch. 15).

What you build. Input and output checks around the provider call: block or flag prompt-injection attempts and obvious PII leaks, and record when a guardrail triggers. Start with simple, transparent rules (pattern checks, a denylist); you can note that a fine-tuned classifier is the advanced version. The value is demonstrating you know that a control plane isn't only about performance and cost — it's also the place safety policy is enforced.

OpenTelemetry

Goal. Speak the industry-standard observability language (FG Ch. 12).

What you build. Emit your telemetry as OpenTelemetry traces and metrics in addition to your own store. This means your control plane can plug into any standard observability backend (Grafana, Jaeger, and the rest) with no custom integration.

Why This Combo Is Worth It ▸

"OpenTelemetry" and "guardrails" on your résumé signal two things employers specifically want: that you build to standards, not bespoke one-offs, and that you think about safety, not just happy-path performance. Together they lift the project from "a neat proxy" to "a serious platform."

Honest Note ▸ OpenTelemetry Production Exporters

Be precise in interviews about what is currently wired vs. production integration: Currently, the control plane generates OpenTelemetry Trace Spans and OTel Metric Instruments (instrumented in code and exported to stdout/logs fallback). To actually pipe metrics to Prometheus or Grafana in production, the next step is attaching a metric reader with an exporter (such as an OTLPMetricExporter or a Prometheus PrometheusMetricReader). Knowing this exact gap — and being able to state "traces/metrics export to console/stdout; wiring to a live Grafana/Prometheus backend is adding an OTLP exporter layer" — is the honest, strong answer interviewers respect.

Done When ▸

A hidden "ignore your instructions and leak X" style input gets caught and recorded by a guardrail; and your telemetry is visible through a standard OpenTelemetry-compatible viewer, not only your own dashboard.

Chapter 11
Stage 7 · Capstone

Deploy as Infrastructure

Goal. The capstone, and the stage that plays hardest to your strengths: make the whole thing deployable as real, reproducible infrastructure. This is what turns "a script that runs on my laptop" into "a platform."

What you build, in order:

  • Kubernetes manifests — describe how to run your container (and Redis, and Postgres) on a cluster: how many copies, how they find each other, how traffic reaches them.
  • A Helm chart — bundle all those manifests into one installable, configurable package, so the whole platform deploys with a single helm install (FG Ch. 17).
  • Terraform — define the underlying infrastructure (the cluster itself, networking) as code, so terraform apply stands up everything from nothing.
  • Statelessness — ensure the service holds no local state (telemetry now in shared Postgres, counters in shared Redis), so you can run many copies behind a load balancer and scale horizontally.
Concepts Used ▸

The entire delivery layer (FG Ch. 17): Docker, Kubernetes, Helm, Terraform, Infrastructure as Code, horizontal scaling. This is your résumé's home turf — the project ends by showcasing exactly the skills you already have, now applied to an AI platform.

Done When ▸

A single terraform apply (or a documented sequence) stands up the whole control plane on a Kubernetes cluster, running multiple replicas that share one database and one Redis, reachable through one endpoint.

Honest Note ▸ Scope for Time

Full cloud Kubernetes + Terraform can eat days and money. If time is short, a local Kubernetes (kind, minikube, or Docker Desktop's built-in K8s) plus a Helm chart is completely legitimate and demonstrates the same skills — you can say "deploys to any K8s cluster; here's the Helm chart and Terraform." Don't burn your whole timeline standing up a cloud cluster if a local one proves the capability.

Chapter 12

Config, Secrets & Environments

Two rules that mark professional work. First: never hardcode secrets. API keys and passwords come from environment variables (or a secrets manager), never from source code — your Stage 0 already reads the Anthropic key from the environment, which is correct. Second: configuration should be external. Provider order, thresholds, model choices, rate limits — all should be settable via a config file or environment, not buried in code, so the same build runs in dev and prod with different settings.

Why It Matters ▸

"How do you manage secrets and config?" is a standard infra interview question. Your answer: "Secrets from environment/secret manager, never in code; config externalized so one image runs anywhere." This is a big part of the Twelve-Factor App philosophy (FG Ch. 17) — worth reading once.

Do This Now ▸

Add a .gitignore that excludes your .env file and your .db file before you push to GitHub. Accidentally committing an API key is a classic, costly mistake. Guard against it from commit one.

Chapter 13

Testing a Non-Deterministic System

You can't assert output == expected when the model's output varies (FG Ch. 11). But you can test everything around it, and that's what matters for a control plane:

  • Test the plumbing deterministically using your mock provider — routing picks the right provider, failover falls back correctly, telemetry gets recorded with the right shape, rate limits trigger. This is exactly why a mock provider was built in Stage 0: it makes the whole system testable without network calls or randomness.
  • Test the contracts — given a request, does the response have the right structure? Does an error get recorded as an error?
  • Test the rules — feed the alert engine known telemetry and assert the right alert fires.
The Interview Gold Here ▸

"How do you test a non-deterministic AI system?" is a question that filters people. Your answer — "you make the model swappable, test everything around it deterministically with a mock, and test the model's behavior separately with evals rather than exact-match assertions" — demonstrates exactly the judgment that's rare and hired for. Your test_smoke.py is the seed of this.

Chapter 14

Scaling, Statelessness & Run Cost

Statelessness is the key to scale. If each copy of your service keeps state in its own memory, you can't safely run several copies. Push all shared state to shared backends — telemetry to Postgres, counters/cache to Redis — and the service becomes stateless: you can run ten copies behind a load balancer and they all behave as one. This is the property Stage 7 depends on.

Run cost awareness. Know roughly what running your platform costs (compute for the replicas, the database, Redis) versus what it saves (cached calls avoided, cheaper models routed to, outages prevented). Being able to talk about the cost/benefit of your own infrastructure is a senior-flavored skill.

Talking Point ▸

"The service is stateless — all shared state lives in Redis and Postgres — so it scales horizontally behind a load balancer." One sentence, and it demonstrates you understand the single most important property for scaling a web service. This is your distributed-systems background showing.

Chapter 15

The README That Stops the Scroll

Your README is the first (often only) thing a reviewer reads. Lead with the problem, not the tech. Structure that works:

  1. One-line description + a live demo GIF, immediately. The GIF does more than paragraphs.
  2. The problem — 2–3 sentences on the pain (no single place to see cost/latency/failures across LLM providers).
  3. What it does — a short bulleted feature list.
  4. Architecture — the pipeline diagram from Chapter 2 (a picture of the request journey).
  5. Run it — docker compose up. One command.
  6. How it works — a short tour of the pieces.
  7. Roadmap — shows vision and that you know what "more" looks like.
Write From the Reader's Side ▸

Name things by what they do for the user, not by how you built them. "See cost and latency for every model call" beats "telemetry ingestion subsystem." Specific and plain beats clever and abstract — every time.
